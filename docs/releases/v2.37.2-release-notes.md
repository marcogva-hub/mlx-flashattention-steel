# v2.37.2 — V34 backward integration bugfix

Patch release fixing a silent SDPA-vjp fallback in the V34 backward
integration shipped in v2.37.0 and v2.37.1.

## What was broken

The v2.37.0 and v2.37.1 release notes advertised:

> D=64 qL ≥ 2048: V34 backward is 1.4-1.85× FASTER than SDPA-vjp

This was true at the kernel level (direct calls to `_ext.v6_nax_*` did
deliver the speedup), but the public `flash_attention()` autograd path
**silently routed through SDPA-vjp** instead of engaging V34 backward,
even when `MFA_ENABLE_V34_BACKWARD=1` was set.

### Root cause

```python
# flash_attention() in mlx_mfa/attention.py, simplified
use_mfa = should_use_mfa(head_dim, qL, causal=False, ...)
# → returns False for non-causal D∈{64,128} on M5 NAX
# (STEEL forward isn't competitive at those shapes)

if not use_mfa:
    return _fallback_sdpa(q, k, v, scale, causal, stream)
    # ^^^ EARLY RETURN: never reaches _make_mfa_custom,
    # so MFA_ENABLE_V34_BACKWARD check never runs
```

The V34 backward env-var check lives inside `_make_mfa_custom`'s
backward closure — but that closure is only constructed if the forward
path goes through `_mfa_forward`.  The early SDPA fallback skipped it
entirely.

### Why it went undetected

All V34 backward correctness tests in `test_flash_attention_v34_backward.py`
called `flash_attention(..., backend="mfa")` to force the MFA path —
which bypasses `should_use_mfa()`.  The default `backend="auto"`
(the user-facing path) was not exercised.

## What's fixed

`mlx_mfa/attention.py` now adds a narrow carve-out before the SDPA
fallback return:

```python
if not use_mfa:
    if (
        backend == "auto"
        and softcap == 0.0
        and alibi_slopes is None
        and not return_lse
        and os.environ.get("MFA_ENABLE_V34_BACKWARD") == "1"
        and _get_has_nax_cached()
        and head_dim == 64
        and q.shape[2] >= 4096
        and q.dtype in (mx.float16, mx.bfloat16)
        and k.dtype == q.dtype
        and v.dtype == q.dtype
        and not causal
    ):
        use_mfa = True  # fall through to MFA path → V34 backward eligible
```

The shape envelope is intentionally narrow: only when end-to-end fwd+bwd
is genuinely faster than SDPA-vjp.

## Engagement envelope (auto, when env=1)

| Config | Backward path | End-to-end vs SDPA-vjp |
|---|---|---|
| D=64, qL ≥ 4096, non-causal, f16/bf16 | V34 backward | **1.81-1.82× faster** |
| D=64, qL < 4096 | SDPA-vjp | V34 loses end-to-end → SDPA preferred |
| D=128, any qL | SDPA-vjp | V34 backward 2.0-2.4× slower (research) |
| Causal | SDPA-vjp / STEEL bwd | V34 backward doesn't support causal (DC3) |

## Measured performance

M5 Max, B=1 H=4 f16, `mx.grad(flash_attention(...))`:

| D | qL | V34 backward (carve-out engaged) | SDPA-vjp | Speedup |
|---|----|---|---|---|
| 64 | 4096 | 2.65 ms | 4.83 ms | **1.82×** |
| 64 | 8192 | 9.78 ms | 17.67 ms | **1.81×** |
| 128 | 8192 | 19.73 ms (NOT engaged) | 19.61 ms | 1.00× (parity by fallback) |

## Correctness validation

V34 backward gradients vs SDPA-vjp (D=64, qL ∈ {4096, 8192}, f16):
- `dq` max|abs| = 0.0000, mean|rel| = 0.20-0.21%
- `dk` max|abs| = 0.0000, mean|rel| = 0.26-0.70%
- `dv` max|abs| = 0.0010, mean|rel| = 0.04%

All within FP16 floor.

## Test coverage

4 new regression tests in `tests/test_flash_attention_v34_backward.py`:

- `test_v34_bwd_v2372_carveout_engages_on_d64_qL4096` — engagement
  proven by non-zero diff vs SDPA-vjp reference
- `test_v34_bwd_v2372_carveout_does_not_engage_below_threshold` —
  qL=1024 must remain bit-identical SDPA-vjp (carve-out skipped)
- `test_v34_bwd_v2372_carveout_does_not_engage_d128` — D=128 must
  remain bit-identical SDPA-vjp (architectural-floor exclusion)
- `test_v34_bwd_v2372_carveout_inactive_without_env` — env-unset case
  preserves default behavior

All 10 V34 backward tests pass.

## Migration from v2.37.0 / v2.37.1

**No code changes required.**  Users with `MFA_ENABLE_V34_BACKWARD=1`
who were silently using SDPA-vjp will now transparently get the V34
backward win on D=64 large shapes.  Other shapes continue to route
through SDPA-vjp as before.

## Investigation context

This bug was discovered while investigating a separate question:
"Does the BK=16 D=128 finding from earlier in the sprint hold?"

Bench data on current source showed BK=16 vs BK=32 gives ~0% difference
at end-to-end (~19.6ms both at D=128 qL=8192), contradicting the
pre-compaction measurement of "BK=16 ~37% faster."  Investigation into
why end-to-end timing didn't vary led to the discovery that both
"V34 ON" and "V34 OFF" gave identical 19.8ms — because both paths
were silently using SDPA-vjp.

The bench discrepancy was a symptom; the silent fallback was the
disease.

## Unchanged

- All v2.37.1 DC12 relaxation (`force_v34` parameter)
