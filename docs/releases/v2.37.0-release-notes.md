# v2.37.0 — V34 backward NAX-direct kernels (SHIP_OPT_IN)

> **Audit retrospective (2026-05-13, v2.37.3):** the D=128 perf table
> below ("V34 backward 2.2-2.4× slower than SDPA-vjp") was measured
> via `backend="mfa"` forced path.  The documented public AUTO API
> (`MFA_ENABLE_V34_BACKWARD=1` + `mx.grad(flash_attention(...))`)
> does NOT engage V34 at D=128 — `should_use_mfa()` returns False
> and the AUTO path falls back to SDPA-vjp at parity.  These D=128
> numbers are research-only kernel characterization, not user-
> facing perf.  See `docs/v6-nax/v2.37.x-perf-claim-audit.md` and
> `CHANGELOG.md` [2.37.3] for the per-claim audit + correction
> trail.  The v2.37.2 carve-out (2026-05-13) reaches D=64 qL ≥ 4096
> only.

Sprint Option β architectural addition: NAX-direct backward attention
kernels for M5+ (dQ + dK + dV).  Apple's NAX backward is NYI in MLX
framework — these kernels are the only path for NAX-accelerated
backward attention on M5+.

## Headlines

- **V34 backward kernels**: dQ (WM=4 Q-row partition), dK + dV multi-SG
  WM=4 split via Q-row partition.  ~1500 LOC of Metal NAX source
  generation.  Correctness validated 116/116 tests.
- **Forward-fusion**: V34 forward writes natural-log lse (BLK1
  infrastructure); `flash_attention()` autograd uses V34 fwd output
  directly without re-compute when V34 backward enabled.
- **SHIP_OPT_IN**: V34 backward available via `MFA_ENABLE_V34_BACKWARD=1`
  env var. Default off (SDPA-vjp fallback preserves v2.36.1 behavior).

## What's new for users

```python
import os
os.environ["MFA_ENABLE_V34_BACKWARD"] = "1"  # opt in

import mlx.core as mx
import mlx_mfa

q = mx.random.normal((1, 4, 8192, 128), dtype=mx.float16)
k = mx.random.normal((1, 4, 8192, 128), dtype=mx.float16)
v = mx.random.normal((1, 4, 8192, 128), dtype=mx.float16)

def loss(q, k, v):
    return mlx_mfa.flash_attention(q, k, v, backend="mfa").sum()

# Now backward routes through V34 NAX kernels (M5+ FP16 D=128).
dq, dk, dv = mx.grad(loss, argnums=(0, 1, 2))(q, k, v)
```

## Performance (M5 Max FP16 D=128 via flash_attention autograd)

| qL | V34 backward | SDPA-vjp | Ratio |
|---|---:|---:|---:|
| 1024 | 1.07ms | 0.50ms | 2.13× |
| 2048 | 3.22ms | 1.54ms | 2.09× |
| 4096 | 12.77ms | 5.31ms | 2.40× |
| 8192 | 48.93ms | 20.37ms | 2.40× |

V34 backward is currently **2.2-2.4× slower** than SDPA-vjp on M5 Max.
Architectural floor analysis indicates the dK kernel is near hardware
peak (FP16 NAX); SDPA-vjp uses a different algorithm (likely fused
single-kernel dK+dV with TGP cross-SG reduction) that V34 backward
would require major restructure to match.

Ship status SHIP_OPT_IN: kernels are validated correct and available
for research / benchmarking via env var.  Default behavior unchanged.

## Architectural validation (Phase 2.O1 + 2.O2)

The session shipped a key empirical finding:

- **Phase 2.O1** (WM=2 K-row partition) FALSIFIED 2026-05-13: 16-24%
  REGRESSION vs WM=1 due to softmax replication tax across SGs (each
  SG redundantly computes Q@K^T + exp).  Reverted.
- **Phase 2.O2** (WM=4 Q-row partition + two-kernel split) shipped:
  intra-SG softmax (no replication), 1.7-2× speedup vs Phase 2 WM=1.

Mechanistic principle: in multi-SG attention backward, partition by
the Q axis (not K) because softmax row-reductions are intra-Q-row.
K-row partition forces every SG to compute the full softmax row, which
duplicates work proportional to WM.

## V34 backward architectural details

- **dQ kernel** (`createV34BackwardQuerySource`, ~880 LOC): per-Q-tile
  dispatch (Q outer), K-tile inner loop, recompute P from lse, compute
  dP = dO @ V^T, dS = P*(dP - D), dQ += dS @ K.  WM=4 Q-row partition
  per Q-tile.  Single-output kernel; each SG writes its 16 Q-rows of dQ
  directly to device.
- **dV kernel** (`createV34BackwardDVSource`, ~330 LOC): per-K-tile
  dispatch, Q-tile inner loop, intra-SG softmax then dV += P^T @ dO.
  Each SG writes its dV partial (BK × D, contributions from its 16
  Q-rows × NQ Q-tiles) to `dV_partials[B, Hq, WM, kL, D]` FP32.  Python
  reduces via `mx.sum(axis=2)` + cast to T.
- **dK kernel** (`createV34BackwardDKSource`, ~440 LOC): same multi-SG
  pattern as dV but adds D = rowsum(dO ⊙ O), dP = dO @ V^T, dS =
  P*(dP - D), and dK += dS^T @ Q.

All three kernels use the V34 forward B+C+E mechanism bundle (cross-SG
sync elimination via `simdgroup_barrier(mem_none)` only, row reductions
via `NAXFrag::row_reduce<SumOp>` simd_shuffle_xor, M5-tuned BQ/BK/WM
defaults bypassing Apple MPP autotune).

## Routing constraint (DC12)

V34 backward auto-routing matches V34 forward routing:
- D=128: always V34-eligible
- D=64 with Nk > 8000: V34-eligible
- D=64 with Nk ≤ 8000: falls back to STEEL backward (legacy v6_nax
  forward path's lse-write is log2-domain, incompatible with V34
  backward's natural-log convention).
